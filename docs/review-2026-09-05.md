# circulusd 프로젝트 검토 — 2026-09-05

초기 검토 기준은 `main`의 `83773587ce6cfed792b83ad282ae6e1cb378c45a`이다. 아래 진단·줄 번호·재현 결과는 수정 전 기준이다. 초기 검토에서는 제품 코드를 수정하지 않고 구조, 현재 구현, 기존 위험 목록, 테스트, 오류 재현을 검토했다. 기존에 있던 미추적 `RISK_REGISTER.md`는 보존하고, 여러 구성 요소의 계약과 외부 검증이 필요한 두 항목만 추가했다. 이후 사용자가 일곱 항목의 수정과 푸시를 요청했으며, 후속 수정 결과는 이 문서 마지막에 기록한다.

circulusd는 상태의 단일 소유권, 커밋 뒤 외부 호출, 세대별 권한 차단, 실행 환경 교체 가능성이라는 설계 원칙이 분명하다. 생산용 구성과 reference 구현을 구분하고, 필요한 구성 요소가 없을 때 공개 서비스를 열지 않는 점도 일관적이다. 현재 완성도는 **핵심 계약을 구현하고 통합을 검증하는 개발 단계**로 평가한다. `cmd/platformd/main.go:250–261`은 현재 production graph와 공개 listener를 명시적으로 거부한다. `docs/acceptance.md`의 §53 전체 적합성 항목에도 아직 최종 PASS가 없다. 개별 실제 workerd 탐색 결과와 전체 운영 적합성은 구분해야 한다.

검증 기반은 상당하다. 이번 실행에서 Go 테스트가 있는 51개 패키지의 race 검사와 vet, TypeScript 34개 테스트 파일의 507개 테스트, 타입 검사, lint, API 계약 검사 및 Python 검사 8개가 통과했다. 그러나 아래 재현처럼 정상 공급자 데이터, 커밋 성공 후 응답 실패, 취소 가능한 context, 직렬화 뒤 크기가 기존 검사에 충분히 포함되지 않았다. 특히 동일한 계약을 구현하는 MemoryStore, celld Repository, Session 상태 코드 사이의 차이를 공동 적합성 검사로 더 강하게 확인할 필요가 있다.

이번 검토는 공개 API/celld, Pi/Worker 상태, 네이티브 실행·RPC, 모델/MCP/effect 경로를 중심으로 했다. 실제 외부 모델 호출, 인프라 변경·배포, 실제 celld crash-durability 및 모든 격리 backend의 운영 적합성 시험은 수행하지 않았다.

**[BUG-001] 정상 Pi 모델 비용과 정수 전용 프로토콜의 불일치**

근거: `workers/pi-runtime/src/engine.ts:694–706`, `workers/pi-runtime/src/pi-agent-core-adapter.ts:519–551`, `packages/protocol-types/src/cbor.ts:50–55`.

Pi 어댑터는 `usage.cost`를 유한한 비음수 숫자로 검사하지만, 그보다 먼저 실행되는 settlement 정규화는 안전한 정수만 허용한다. 설치된 `@earendil-works/pi-ai@0.84.3`의 `dist/models.js:527–544`는 백만 토큰당 요율을 사용해 소수 비용을 만든다. OpenAI, Anthropic, Google 공급자 코드가 이 함수를 호출한다.

재현에서는 입력 요율 1, 출력 요율 2, 입력 토큰 10, 출력 토큰 1을 실제 `calculateCost`에 전달했다. 생성된 `cost.input=0.000009999999999999999`를 포함하는 응답은 `engine.step()`에서 아래 오류로 거부되었다. 비용만 모두 0으로 바꾼 같은 응답은 `turn_complete`에 도달했다.

```text
INVALID_CONTEXT
stepContext.settlement.outcome.result is not a bounded protocol value:
$.message.usage.cost.input: numbers must be safe integers; floating-point values are unsupported
```

영향은 이미 끝난 정상 모델 호출을 settlement로 반영하지 못하는 것이다. 기존 Pi 테스트의 비용 fixture는 모두 0이어서 이를 발견하지 못했다. 수정 시 외부 Pi 응답과 내부 저장 표현 사이에 단위·버전·정밀도가 정의된 변환을 두고, checkpoint 재구성과 실제 공급자 형식까지 검증해야 한다. 비용을 임의로 0으로 만들거나 전역 CBOR 규칙만 완화하는 방식은 피해야 한다. `RISK_REGISTER.md`에도 같은 ID로 등록했다.

**[BUG-002] stdin 쓰기와 닫기가 취소에 반응하지 않음**

근거: `internal/sandboxd/supervisor.go:545–556,575–581`, `internal/sandboxrpc/server_linux.go:673–688`, `internal/sandboxrpc/protocol.go:21–23`.

`WriteStdin`은 mutex를 잡고 blocking pipe `Write`를 실행하며 context는 진입할 때만 확인한다. `CloseStdin`도 같은 mutex를 기다린다. 실제 기본 sandboxd 구성은 이 exec runner를 사용한다.

`/bin/sleep 30`을 `StdinStream`으로 실행하고 50 ms context에서 64 KiB 쓰기를 최대 두 번 수행했다. 150 ms 뒤에도 쓰기가 남아 있었고, 별도의 50 ms context로 요청한 닫기도 150 ms 뒤까지 반환하지 않았다. 명시적으로 자식 프로세스를 kill한 뒤에만 해제되었다. 64 KiB는 허용된 RPC chunk 크기이며 프로세스 timeout은 최대 24시간이다.

영향은 호출자의 취소 이후에도 handler와 버퍼가 남고, 후속 stdin 요청까지 막히는 것이다. 쓰기의 취소·deadline과 부분 쓰기 결과를 명시적으로 처리하고, stdin 닫기가 정체된 쓰기 mutex 때문에 무기한 대기하지 않도록 해야 한다. RPC의 chunk 멱등성과 부분 쓰기 의미도 함께 검증해야 한다.

**[BUG-003] durable 커밋과 live 이벤트 전달 사이의 복구 공백**

근거: `internal/platformapi/celldrepo/repository.go:168–184`, `internal/celld/host.go`의 `FaultAfterBarrier` 및 receipt replay 경로.

`AppendDurableEvent`는 host 호출이 성공했을 때만 publish하고, `Result.Replayed`인 경우 전달을 건너뛴다. 커밋과 durability barrier 뒤에 응답 오류가 발생하면 이벤트는 저장되지만 전달되지 않는다. 동일 명령 재시도는 receipt replay로 성공하면서 다시 publish를 생략한다. 기존 구독을 닫지도 않는다.

재현은 sequence 1까지 읽고 live 구독을 연 뒤 sequence 2의 `turn.completed`를 append할 때 `FaultAfterBarrier`에서 한 번 실패시켰다. 동일 command ID 재시도는 `replayed=true`, sequence 2로 성공했다. ReplayEvents에는 sequence 2가 있었으나 기존 구독 채널은 열린 채 비어 있었다.

영향은 저장된 완료 이벤트가 현재 구독자에게 조용히 누락되는 것이다. 이 저장 계층의 live 구독 계약 위반이며, 현재 HTTP 경로가 이미 이 어댑터를 공개하고 있다는 주장은 아니다. 불확실한 커밋 결과에서는 구독을 닫아 재조회하게 하거나, 구독별 cursor와 durable notification을 통해 전달을 복구해야 한다. replay를 무조건 다시 broadcast하면 중복 전달이 생길 수 있으므로 전달 멱등성과 함께 설계해야 한다. 실제 저장소 장애·재연결에서도 검증해야 하므로 `RISK_REGISTER.md`에 등록했다.

**[BUG-004] celld 저장 경계에서 권한 범위 필드가 누락됨**

근거: `internal/platformapi/celldrepo/repository.go:117–125,157–162`, `internal/platformapi/celldrepo/aggregate.go:138–179`. 비교: `internal/platformapi/memory.go:106–114,342–378`.

CreateTurn은 permit의 operation과 비어 있지 않은 proof를 확인하지만 permit의 principal과 session을 비교하지 않는다. 생성 명령에도 tenant와 permit의 principal/session이 들어가지 않는다. AppendDurableEvent의 인코딩에서는 authority의 tenant, user, runtime revision, workspace가 빠지고 세대 번호와 turn만 남는다.

다른 tenant·subject·session용 permit을 원래 세션의 CreateTurn에 넣었는데 턴이 생성되었다. 별도 재현에서는 tenant·user·runtime·workspace만 바꾼 event authority로 원래 세션에 sequence 1을 커밋할 수 있었다. MemoryStore의 동등한 경로에는 해당 비교가 있다.

현재 상위 Service의 authorizer가 별도로 존재하고 production public graph는 열려 있지 않다. 따라서 이는 외부에서 바로 악용 가능한 공개 API 취약점으로 입증한 결과가 아니라, Repository 대체 구현이 기존 권한 계약을 지키지 않는 결함이다. 필요한 범위 필드를 aggregate 명령에 보존하고, authoritative state와 같은 트랜잭션 안에서 비교해야 한다. 공동 conformance에는 세대 mismatch 외에 교차 principal/session/runtime/workspace 사례도 포함해야 한다.

**[BUG-005] 출력 역압력 오류를 두 소비자가 경쟁해서 읽음**

근거: `internal/sandboxd/supervisor.go:518–526,802–816`, `internal/sandboxrpc/server_linux.go:645–648`, `internal/sandboxrpc/client_linux.go:292–294`.

Attach가 취소 가능한 context를 받으면 watcher가 `<-subscriber.done`을 기다린다. 이 채널은 공개 `Attachment.Done`과 같고 `ErrOutputBackpressure`는 한 번만 들어간다. watcher가 먼저 읽으면 실제 소비자는 닫힌 채널의 기본값 `nil`을 받는다. RPC는 이를 정상 종료로 반환하며 client도 terminal event가 없는 정상 EOF를 별도로 거부하지 않는다.

`FakeRunner`, `SubscriberBuffer:1`, `ReadChunkBytes:1`로 연결하고 소비를 늦추면서 출력을 발생시켰다. Background context에서는 오류가 보존됐지만 WithCancel context에서는 20/20회 오류가 사라졌다. 기존 역압력 테스트는 Background context를 사용한다.

완료 알림은 여러 소비자가 볼 수 있는 별도 채널로, 종료 오류는 불변 결과로 보관하는 식으로 분리해야 한다. 출력 유실이 정상 완료처럼 보이지 않도록 실제 RPC의 취소 가능한 context 경로도 검증해야 한다.

**[BUG-006] 모델 결과의 직렬화 크기와 ledger 저장 한도가 맞지 않음**

근거: `internal/modelgateway/session_dispatch.go:55–58,289–299`, `internal/effectledger/reference.go:354–355`. 비교: `internal/mcpgateway/session_dispatch.go:45–49`.

모델 starter 생성자는 ledger 용량과 gateway 출력 한도의 호환성을 확인하지 않는다. 응답 크기, 이벤트 크기, ledger 결과 한도를 각각 1 MiB로 설정하고 정상 completion text로 `<` 200,000개를 반환했다. 공급자 응답 자체는 허용되지만 `json.Marshal`이 `<`를 `\u003c`로 바꾸어 결과가 최소 1,200,000바이트로 커졌다. 결과 저장은 실패했다.

재현에서 공급자는 정확히 한 번 호출됐으며 ledger는 `accepted`이고 terminal 결과는 없었다. 한 번만 실행할 권한은 이미 소비됐고, 이 공급자에 durable retrieval도 없으므로 재호출로 안전하게 복구할 수 없다. 1 MiB는 기존 모델 테스트 helper가 주는 ledger 한도이며 production 기본값으로 정해져 있다는 의미는 아니다.

생성 단계에서 직렬화 envelope, 문자열 escape, 도구 인자 인코딩을 포함한 최악의 결과 크기가 저장 한도 안에 들어오는지 검증하거나, 큰 결과를 별도 저장하고 참조로 남겨야 한다. 단순히 원본 문자열 길이와 ledger 크기만 비교하면 재발한다. 작은 출력에서도 발생하는 잘못된 용량 구성과 경계 크기 출력을 함께 검증해야 한다.

**[BUG-007] stream 정리를 완료 결과 저장보다 먼저 무제한 기다림**

근거: `internal/modelgateway/session_dispatch.go:266,293–299`, `internal/modelgateway/provider.go:50–60`.

모델 completion을 받은 뒤 context가 없는 `Stream.Close()`를 동기로 호출하고, 그 호출이 끝나야 terminal fact를 저장한다. Close를 지연시키는 provider stub을 사용하자 consumer의 1초 deadline이 지난 1.1초 시점에도 호출이 끝나지 않았고 ledger에는 acceptance만 있었다. Close 대기를 풀면 완료됐다.

재현은 지연을 주입한 provider 계약 검사다. 이 패키지에는 실제 네트워크 provider가 아직 없으므로 특정 실제 공급자에서 발생했다고 확인한 것은 아니다. 완료 결과의 기록을 지연 가능한 정리에 종속시키지 않고, adapter의 Close에도 제한된 정리 시간과 종료 책임을 정의해야 한다. 타임아웃 시 반환만 하고 뒤의 goroutine을 방치하는 방식은 자원 회수를 보장하지 못한다.

권장 작업 순서는 BUG-001/002/003의 회귀 재현을 먼저 고정한 뒤, BUG-004/005/006/007을 각자 검토·되돌릴 수 있는 작업 단위로 해결하는 것이다. 그다음 기존 Unit 11/12 계획에 따라 실제 celld 저장·복구와 공개 API, 단일 실행 backend를 연결한 경로를 검증하는 편이 현재의 통합 공백을 줄이는 데 도움이 된다. 이미 알려진 `STATE-001`, `API-001`, `BOOT-002` 및 실제 backend 적합성 공백은 신규 버그로 다시 세지 않았다.

검증과 재현 기록은 다음과 같다. 기존 검사는 모두 통과했고, API 추가 테스트는 올바른 동작을 기대하도록 작성하여 현재 결함 세 건에서 실패했다. 모델 추가 테스트는 결함 현상을 관찰하는 assertion이므로 종료 코드가 0이다. 재현을 위한 제품 소스 수정이나 영구 테스트 추가는 하지 않았다.
